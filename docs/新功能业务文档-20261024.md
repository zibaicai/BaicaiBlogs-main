## 3. 摘要功能

### 3.1 字段规则

- 不新增 `subtitle` 字段。
- 继续使用现有 `description` 作为摘要。
- `description` 同时用于：
  - C 端文章详情；
  - 首页文章卡片；
  - 搜索预览；
  - SEO 描述；
  - 标签/推荐辅助。

### 3.2 当前问题与澄清

- 管理端文章列表，每张卡片标题下方的灰色文字不是副标题，而是 `post.slug`。
- slug 来源：
  - 新建文章默认 `post_${timestamp}`；
  - 上传 MD 时通常取文件名；
  - 当前编辑器没有 slug 编辑入口；
  - 修改 slug 会影响 URL。
- 管理端「文章」页面标题下方的「可见性决定 C 端是否展示」是页面硬编码说明文案，不是文章副标题。
- 摘要输入测试未发现保存问题。
- 真正的问题是：
  - 摘要输入框位置不显眼；
  - C 端文章详情没有展示摘要；
  - 用户容易把 slug 误认为副标题。

### 3.3 改进要求

- 管理端把摘要输入从右侧属性栏移到文章标题下方，作为主编辑区字段。
- 新建/编辑均可录入。
- 建议多行，0–200 字，显示字数。
- 保存时写入 `description`。
- C 端文章标题下方展示摘要。
- 摘要为空时，可从正文前 80–120 字生成兜底摘要。
- 首页卡片、搜索继续复用 `description`。
- 不新增数据库字段。
- 不把 slug 当作副标题展示；如需展示 slug，应明确标注「slug / 链接标识」。

## 4. 说说功能

### 4.1 后端现状

后端已有：

```text
GET    /api/public/chatters
GET    /api/public/chatters/page
GET    /api/public/chatters/{slug}
POST   /api/admin/chatters
PUT    /api/admin/chatters/{slug}
DELETE /api/admin/chatters/{slug}
```

`ChatterRequest` 现有字段：

```text
slug
title
content
mood
cover
date
tags
```

后端已有基础 CRUD，缺的是管理端 UI、权限字段和可见性过滤。

### 4.2 管理端需求

- 左侧导航新增「说说」。
- 列表支持：
  - 全部；
  - 草稿；
  - 私密；
  - 公开。
- 支持新建、编辑、删除。
- 支持保存草稿、发布。
- 发布时选择：
  - 公开；
  - 私密。
- 编辑字段：
  - 标题；
  - 内容；
  - 心情；
  - 封面；
  - 日期；
  - 标签。
- 可复用 `MetaMatrix` 的 `type="chatter"`，其已支持心情和标签。

### 4.3 可见性规则

建议数据模型：

```text
status: DRAFT | PUBLISHED
visibility: PUBLIC | PRIVATE
user_id
```

规则：

| 状态 | 可见范围 |
|---|---|
| 草稿 DRAFT | 仅管理端拥有者本人 |
| 已发布 + 私密 | C 端登录后仅拥有者本人可见 |
| 已发布 + 公开 | 所有人可见 |

- 草稿不进入 C 端。
- 普通管理员不能查看别人的私密说说。
- 超级管理员可以兜底查看，但必须走审计。
- 私密说说在 C 端的入口仍在 `/moments`。
- 拥有者登录后显示「全部 / 公开 / 私密」Tab。
- 访客只看到「公开」。
- 私密 Tab 只对拥有者显示。

### 4.4 超级管理员审计兜底

采用：

```text
拥有者 + 超级管理员审计兜底
```

不沿用照片墙的申请/授权逻辑，原因：

- 私密说说更接近日记；
- 照片墙授权是资源分享逻辑；
- 日记如果可申请、可授权，会改变语义；
- 超级管理员只用于数据恢复、违规处理、法律要求等兜底场景。

审计要求：

- 只读，不可修改；
- 不改变 `updated_at`；
- 不产生用户通知；
- 不产生阅读状态；
- 用户完全不可察觉；
- 必须填写查看原因；
- 记录：
  - 操作者；
  - 时间；
  - IP；
  - 资源 ID；
  - 查看原因。
- 查看入口不放在普通列表；
- 单独做「隐私查看 / 兜底查看」入口。

## 6. TOC

### 6.1 内容范围

- 取 `h1–h6`。
- 不显示 `01/02/03` 编号。
- 多个 h1 时使用折叠分组，避免目录过长。

### 6.2 折叠规则

```text
▼ 第一章标题
    子标题
    子标题
        三级标题
▶ 第二章标题
▶ 第三章标题
```

- 每个 h1 是一个折叠组。
- 默认只展开当前阅读组。
- 点击 h1 展开/收起。
- 滚动到某一组时自动展开。
- 多个 h1 之间增加分隔线或较大间距。
- 当前阅读标题高亮。
- 目录不显示编号，避免观感像列表。

### 6.3 层级视觉

用字号 + 透明度 + 小缩进区分；缩进最多 16px。

```text
H1  13px  加粗       缩进 0
H2  12px             缩进 4px
H3  11px             缩进 8px
H4  10px             缩进 12px
H5   9px  低透明度    缩进 14px
H6   9px  低透明度    缩进 16px
```

- 缩进封顶 16px，防止 h6 没有文字宽度。
- h5/h6 主要靠透明度弱化。

### 6.4 吸顶规则

需求：

```text
导航栏可见：TOC 距离导航栏底部 10px
导航栏隐藏：TOC 距离视口顶部 10px
```

实现建议：

```css
.article-toc {
  position: sticky;
  top: 74px; /* 64px 导航 + 10px */
}

body[data-nav-hidden="true"] .article-toc {
  top: 10px;
}
```

- 导航栏回弹时，TOC 下移；
- 导航栏隐藏时，TOC 上移；
- 可加 `transition: top .2s`。
- 点击目录滚动时使用 `scroll-margin-top` 或动态偏移，避免标题被导航栏遮挡。
- TOC 最大高度 `calc(100vh - 90px)`，超出可滚动。
- sticky 父容器不能有 `overflow: hidden`。

### 6.5 无标题情况

- 文章没有 h1–h6 时，TOC 不显示或显示空状态。
- 建议直接隐藏 TOC 卡片。

### 6.6 待定

- 移动端 TOC 是否折叠、是否吸顶，尚未定稿。
- 建议移动端放在文章标题后，非 sticky 或折叠。

## 8. 主题系统

### 8.1 目标

- 全站默认主题；
- 日间/夜间；
- 访客可自定义完整调色板；
- 从背景图提取推荐色；
- 主题配置抽离成 CSS Token；
- 不直接覆盖 Tailwind 原始色板。

### 8.2 主题来源与决策

- 主题色默认由背景图取色推荐。
- 背景切换只更新推荐，不自动修改当前主题。
- 管理员/访客手动确认后生效。
- 默认日间/夜间主题已经够用。
- 自定义属于高级功能。
- 自定义整套调色板可能造成观感变差，需要提醒。
- 全站一个默认主题，但访客可本地覆盖。
- 访客自定义保存在本地，不写回站点配置。

### 8.3 一套还是两套自定义

最终采用：

```text
两套自定义主题
日间一套
夜间一套
```

原因：

- 一套无法同时适配日间/夜间；
- 一套会导致切换模式必须重置；
- 两套可以独立保存；
- 夜间不会因为日间自定义而不可读；
- 日间/夜间开关不再弹“重置主题”提示。

UI：

```text
外观
[日间] [夜间]

主题来源
(●) 默认主题
( ) 自定义主题

[从另一模式复制]
[恢复当前默认]
[恢复全部默认]
```

- 两套独立保存。
- 无自定义的槽位继续使用默认主题。
- 可复制到另一模式，快速复用。
- 日间/夜间切换不重置。

### 8.4 恢复默认

- 当前模式恢复：只重置当前模式。
- 文案动态：
  - `恢复日间默认`
  - `恢复夜间默认`
- 全部恢复：单独放危险操作区，二次确认。
- 一键初始化主题：恢复默认主题/调色板，不影响背景。

### 8.5 完整调色板 Token

建议暴露语义 Token：

```text
背景
背景柔和层
卡片/表面
次级表面
正文
次要文字
边框
主题色
主题色上的文字
链接
焦点环
成功 / 警告 / 危险
```

不允许直接暴露任意 CSS 字符串，只允许合法颜色值。

### 8.6 背景取色

- 从当前背景图提取 5–6 个候选色；
- 服务端提取，避免 CORS；
- 推荐色不是直接主题色；
- 自动调整亮度/饱和度；
- 检查文本对比度；
- 自动生成：
  - accent；
  - accent-strong；
  - accent-soft；
  - accent-border；
  - accent-contrast；
  - link；
  - ring。
- 深色/浅色分别生成可读色板。
- 背景轮播切换只更新推荐。

### 8.7 Tailwind 实现原则

不能只覆盖 Tailwind 原始色板：

```css
--color-slate-900
--color-indigo-500
```

原因：

- 原始色阶不是语义色；
- 改一个色阶会影响正文、标题、边框、图标；
- 透明度/暗色组合无法稳定覆盖；
- 状态色会被误伤。

正确方式：

```css
:root {
  --ui-bg: ...;
  --ui-surface: ...;
  --ui-text: ...;
  --ui-muted: ...;
  --ui-border: ...;
  --ui-accent: ...;
}

@theme {
  --color-bg: var(--ui-bg);
  --color-surface: var(--ui-surface);
  --color-ink: var(--ui-text);
  --color-muted: var(--ui-muted);
  --color-line: var(--ui-border);
  --color-accent: var(--ui-accent);
}
```

组件使用语义类：

```text
bg-bg
bg-surface
text-ink
text-muted
border-line
bg-accent
text-accent-contrast
```

现状：

- 项目使用 Tailwind 4.1；
- 大量组件仍写死 `bg-white/40`、`dark:bg-slate-800/50`、`text-slate-900`、`text-indigo-500`；
- 需要逐步替换为语义 Token；
- 状态色、代码高亮、图片/插画保持固定或单独 Token。

## 9. 分类体系

### 9.1 规则

- 分类多级；
- 最大 4 级；
- 管理员创建默认分类；
- 一个资源只属于一个主分类；
- 资源必须选择一个**根分类**；
- 深层子分类可选，不强制；
- 一个资源可以有 N 个 Tag；
- 采用方案 B（根 Tab + 嵌套分类选择）。

### 9.2 数据模型建议

```text
categories
├─ id
├─ name
├─ slug
├─ parent_id
├─ path
├─ depth
├─ is_root
└─ sort

resources
├─ category_id   // 必填，可以是根或后代
└─ tags[]
```

校验：

- `category_id` 必填；
- 根分类允许；
- 子分类必须可追溯到同一根；
- 禁止循环父子关系；
- 删除分类前必须迁移资源；
- 根分类不能直接删除；
- 深度不超过 4。

### 9.3 根目录资源页

- 默认「全部」；
- 根 Tab 只显示**有资源的根分类**；
- 根分类下只要有任意后代资源，就显示该根 Tab；
- 进入根分类后，显示子分类选择器；
- 子分类选择器只显示有资源的路径；
- 分类路径以完整形式显示在资源卡片上：

```text
技术 / 前端 / React
```

- 资源卡片添加分类标识；
- 根分类资源进入该根分类；
- Tag 继续用于搜索和筛选。

### 9.4 方案 B 的界面

```text
[全部] [技术 12] [生活 8] [随笔 5]
```

进入「技术」后：

```text
技术
[全部] [前端] [React] [性能]
```

- Tab 只显示有资源的根分类；
- 子分类只显示有资源的路径；
- 卡片显示完整分类路径；
- 支持面包屑。

## 10. Tag 体系

### 10.1 规则

- Tag 完全扁平；
- 不做层级；
- 不做 Tag Group；
- 一个资源可以绑定多个 Tag；
- Tag 由管理员维护；
- 用户可申请新 Tag；
- 用户只能给自己的资源加 Tag；
- 用户无权修改别人的资源。

### 10.2 Tag 数据模型建议

```text
tags
├─ id
├─ name
├─ slug
├─ status       ACTIVE / PENDING / REJECTED / MERGED
├─ alias_of
├─ created_by
├─ approved_by
└─ usage_count
```

- 待审批 Tag 不能绑定资源；
- 被拒绝/停用 Tag 不能使用；
- 同义 Tag 合并到已有 Tag；
- 重复申请合并处理。

### 10.3 Tag 申请流程

```text
用户填写 Tag 名称 + 理由
→ 进入待审核
→ 管理员审批
   ├─ 通过：进入 Tag 库
   ├─ 拒绝：站内信 + 拒绝理由
   └─ 已存在：合并/别名，通知用户
→ 申请人收到站内信
→ 用户自行在资源里添加
```

- 申请是全局申请，不绑定具体资源；
- 审批通过后**不自动绑定**到任何资源；
- 避免申请未成功时资源已挂 Tag 的负担；
- 通过后用户可去自己的资源添加该 Tag。

### 10.4 站内信

- 通过：通知 Tag 已进入库，可添加；
- 拒绝：通知被拒绝，并附理由；
- 重复/合并：通知已合并到已有 Tag；
- 站内信字段建议：

```text
user_id
type
title
body
link
read_at
created_at
```

### 10.5 Tag 推荐

资源选择分类后，Tag 输入区显示相关 Tag：

```text
相关标签
[React] [Hooks] [性能] [源码] [前端工程化]
```

优先级：

1. 同分类子树高频 Tag；
2. 与当前已选 Tag 共现的 Tag；
3. 父分类常见 Tag；
4. 全站热门 Tag；
5. 标题/摘要关键词匹配。

规则：

- 只推荐 `ACTIVE`；
- 排除已选 Tag；
- 排除停用、待审批、被合并 Tag；
- 每次 6–8 个；
- 点击添加，不自动添加；
- 分类无数据时回退全局热门；
- 无分类时提示先选分类；
- 支持「换一批」。

### 10.6 推荐会话

开始：

- 打开标签选择面板；
- 已选择分类。

结束：

- 关闭标签选择面板；
- 保存资源；
- 取消编辑；
- 切换分类。

会话规则：

- 维护 `seenTagIds`；
- 每次推荐排除已看过的 Tag；
- 同一会话不重复；
- 切换分类清空 `seenTagIds`；
- 已选 Tag 即使取消选择，本轮也不再推荐；
- 候选耗尽显示「本轮推荐已看完」；
- 提供「重新浏览」或「手动搜索」；
- 「重新浏览」才清空已看集合；
- 状态不跨保存持久化。

### 10.7 Tag 推荐后端

建议维护：

```text
category_tag_stats
├─ category_id
├─ tag_id
├─ usage_count
└─ updated_at
```

避免每次实时扫全表。

## 13. 关键流程

### 13.1 说说发布

3. 保存草稿或发布；
4. 发布选择公开/私密；
5. 公开进入 C 端 `/moments` 公开 Tab；
6. 私密仅拥有者 C 端可见；
7. 草稿只在管理端。

### 13.2 Tag 申请

1. 用户提交全局 Tag 申请；
2. 管理端待审批；
3. 通过进入 Tag 库；
4. 发送站内信；
5. 用户到自己的资源添加；
6. 不自动绑定资源。

### 13.3 Tag 推荐

1. 资源选择分类；
2. 打开 Tag 选择器；
3. 系统按分类/共现/热门推荐；
4. 点击添加；

- 用户无感知。

- 不显示编号；
- h1 可折叠；
- 多 h1 分组；
- 点击滚动正确；
- 吸顶动态跟随导航；

- 手动确认生效；

- 恢复当前/全部；

- 根 Tab 只显示有资源的根；

## 17. 未决事项

1. 移动端 TOC 的具体形态：折叠/隐藏/非 sticky。
2. Tag 推荐的具体权重和数量上限（当前建议 6–8）。

8. 超级管理员审计入口的具体 UI 位置。
9. 文章 slug 是否需要在编辑器中开放修改；当前讨论只确认它是 slug，不是副标题。
10. 音乐工具行在首页的显隐按钮是否禁用。
